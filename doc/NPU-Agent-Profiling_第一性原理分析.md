# 性能分析Agent辅助方案分析 - 2026/11/09

## 1. LMBench工作现状
LMBench当前用例条数超过200，在每个项目都是性能重点工作，每条用例都需要进行ESL仿真并达成性能目标，未达标用例要求分析明确根因。

## 2. 当前的关键痛点
1. **人力资源消耗太大**: 每个未达标用例都依赖观察指标A->指标B->指标C->指标D->得到最终结论的重复流程，大量精力被限制在简单场景问题的重复定位;
2. **分析经验缺乏沉淀**: 一个经验丰富的老员工熟悉部分问题的分析讨论，能快速开展分析，但一个新员工或者之前没有分析过这类问题的员工，遇到这类问题时往往没有头绪;
3. 复杂问题定位困难: 部分问题涉及模块多、特性深, 可能引起多个问题表象，需要抽丝剥茧才能定位到问题根因;

** 早期希望构造一个提供简单背景知识，让Agent发挥能力端到端解决问题的框架，目前来看效果不好。**

## 3. 从第一性出发，Agent到底能解决什么问题？怎么解决？

Agent辅助性能分析最终目标 —— 在一个白盒、可任意扰动、但每次查询成本高昂的系统上，以最小总成本（仿真小时 + 人工分钟 + 工程量）产出经过验证的性能瓶颈归因。

### 3.1 Agent的独特价值

如果把性能分析过程定义为`仿真->观察指标A->指标B->查看架构文档->指标C->指标D->查看debug日志->得到最终结论`的重复流程，其中哪些部分是脚本不能做，agent可以做，并且可以带来价值和效率提升的？

| 环节 | 执行者 | 为什么无可替代 |
|---|---|---|
| 问题分析链上每步“下一步看什么”的提议 | LLM | 决策依赖当前已验证发现，写不成固定脚本；且LLM包含通用微架构先验知识，可能提供超出工程师的分析能力|
| 历史链的语义匹配与跨情境改编 | LLM | “signature前缀像哪条链”是模糊匹配，关键词检索做不到；LPDDR 的链改编到 HBM 也是它的活 |
| 非结构化知识（问题单、文档、采访）的消化 | LLM | 形式化劳动可以从人转移到机器 |
| 知识采集的形态转换 | LLM | 纠错模式（人生成难、纠错易）、卡壳即采集（动机最高时刻）、case 文档自动成稿 |
| 数据解析、算术、每步验证 | 脚本 | 确定性、可回归 |
| 达标判决 | 脚本 | LLM 无权下结论——这是整个方案的信任底线 |
| 机制、根因确定 | 人 | 定位之后专家几分钟走完结果确认 |

形式化劳动 —— 把分析过程描述成规则化、系统化的统一格式。
知识库形式的工作总是死在一个地方，它们都要求人以结构化形式贡献知识，而人在结构化写作上的成本高到没人愿意干。

### 3.2 框架方案

```
────────────────────────────────────────
层次: L0 IR 层 -- 当前已有，解析脚本，后续整理成一个统一格式，提供agent通用访问接口
职责: 把原始 trace/counter封装成一组一键可算的标准视图：利用率矩阵、各资源账本分解、地址-通道映射拟合等。所有数据加工、算术、验证都在这层完成
执行者: 脚本
与原架构的关系: 原 L0 改造 + 原 L2解散后各类账本并入此层。关键变化：不再预先设计完备的中间表示，视图按诊断需要增量开发，新视图需求进工程任务队列按价值排序
────────────────────────────────────────
层次: L1 期望层
职责: 为每条 benchmark 计算预期值 + 误差带。实测落在带内 → 自动关闭；落在带外 → 送入诊断层。承担 100+
  条测试的自动分流
执行者: 脚本
与原架构的关系: 原 L1 瘦身：以 roofline 为主，历史基线有则用，跨测试一致性降为可选
────────────────────────────────────────
层次: L2 诊断层
职责: 唯一的 agent/LLM 层。对每个进入的 case 逐步定位：检索历史分析链 → 生成下一步要查看的视图（附出处）→ 交 L0
  计算 → 结果经机械验证后追加为链上新节点 → 循环，直到产出定位结论（位置、现象类别、量化、证据链、置信度）。原
  L2 的瓶颈识别保留为本层固定的起手步骤（先看差距报告、再看利用率矩阵）
执行者: LLM 提议，数据裁决
与原架构的关系: 原 L3 转型 + 吸收原 L2 的起手步骤。边界：不产出机制、根因、修复；定位不了如实上报
────────────────────────────────────────
层次: L3 沉淀层
职责: 每个关闭的 case 以统一结构归档（分析链 + 定位结论 + 专家补充的机制与修复）；为新 case
  提供与历史链的检索匹配；维护链记录状态（已验证/未验证/已过时）与命中统计；输出全套件资产负债表
执行者: 脚本存取，LLM 做语义匹配
────────────────────────────────────────
```

每一步循环：
```
  当前发现（已验证）→ LLM 提议下一步该看什么（2-3 个候选视角）
                    → 脚本计算 → 结果回填为新的已验证节点
                    → 直到定位结论 / 或给出最佳推测
```


### 3.3 分析链形式
```
{
  "case_id": "case-003",
  "meta": { "日期": "2026-11", "芯片版本": "X9-v0.9", "benchmark": "bw_gather" },
  "signature": {
    "现象类别": "负载不均",
    "特征": { "瓶颈资源": "DRAM通道",
              "dmc.rd_bw.max": 99,
              "dmc.rd_bw.min": 0.5,
              "dmc.rd_bw.var": 1800,},
    "入口发现": "实测带宽 26% of 预期"
  },
  "chain": [
    { "step": 1, "view": "bench.gap_report",
      "finding": "实测 15.8 vs 预期 60 GB/s" },
    { "step": 2, "view": "utilization.matrix",
      "finding": "DMA 41%, NoC 38%, CH0 99%, 其余通道 <2%",
      "rationale": "带宽低先逐级看利用率定位瓶颈资源" },
    { "step": 3, "view": "mc.slot_ledger(ch=0)",
      "finding": "CH0 有效载荷 94%, row 命中 96%, 自身健康",
      "rationale": "区分资源自身效率与流量分布",
      "被排除分支": [ { "候选": "CH0 硬件慢", "排除依据": "槽位账健康" } ] },
    { "step": 4, "view": "trace.channel_mapping_fit",
      "finding": "97% 请求映射 CH0, 与文档公式吻合" }
  ],
  "conclusion": { "locus": "地址-通道交织映射", "现象": "单通道混叠",
                  "量化": "损失 43 GB/s", "置信度": "高" },
  "human_appendix": {
    "机制": "2KB 交织粒度 × 32KB 行距（周期整数倍）→ 混叠",
    "修复": "行距 pad 2KB / 评估 XOR hash",
    "坑": "所有 2 的幂 pitch 的 tiled 负载都暴露"
  },
  "status": "expert-verified",
}
```
signature 管匹配，status 管可信。

signature（签名）——这条 case 的“身份证”

存的是症状的结构化特征，唯一目的是：新 case 进来时，机器能快速判断“它和哪条历史 case 长得像”。对应 case-003 里的：
```
"signature": {
  "现象类别": "负载不均",              ← 病的类别（状态式命名，不带“损失”后缀）
  "特征": { "瓶颈资源": "DRAM通道",   ← 病在哪个器官
            "dmc.rd_bw.max": 99,     ← 体检报告的关键数字（counter 路径做键）
            "dmc.rd_bw.min": 0.5,
            "dmc.rd_bw.var": 1800,},  ← 判别线：自身效率正常 → 负载不均；偏低 → 资源效率低
  "入口发现": "实测带宽 26% of 预期"   ← 最初的症状
}
```

status（状态）——这条记录现在还可不可信

知识会过时：芯片版本迭代后，一条当年正确的链可能悄悄变错。status 是每条记录的保鲜标签，随时间被维护：

| 环节 | 执行者 |
|---|---|
|expert-verified|专家确认过，可信|
|unvalidated|agent 走出来的，还没人背书，用时要谨慎|
|stale|新版本上重放后发现不复现，已过时，降权|


维护机制：每次仿真器出新版本，把历史链在回归套件上重放——发现能复现就续期，不能就标 stale。检索时 stale 的链排在最后甚至不进候选，防止过时知识毒害新诊断。

### 3.4 分析链使用过程

```
新 case 进入诊断
   │
   ├─ 第1步：此时只有入口发现（“实测带宽 22% of 预期”）
   │         → 只能做一次很弱的检索，仅供参考
   │
   ├─ 第2步：跑固定的起手视图（差距报告 + 利用率矩阵）
   │         → 现在知道瓶颈资源、利用率长什么样了
   │         → 这时才做真正的检索，能命中 case-003 这样的历史链
   │
   ├─ 第3步：之后每验证出一个新发现，
   │         如果下一步不知道看什么了（卡壳），就带着新发现重新查一次
   │
   └─ 命中历史链后：照着它下一步的走法走；
            走着走着对不上了 → 从对不上的地方开始自己判断
```

起手视图: 不管什么 case 进诊断层，头两步永远是固定的、不看 LLM 意见

**第 1 步：差距报告（bench.gap_report）**

这个 benchmark 预期性能多少、实测多少、差多远。对应 case-003 的 step 1：“实测 15.8 vs 预期 60 GB/s”。

**第 2 步：利用率矩阵（utilization.matrix）**

把所有资源（DMA、NoC、各 DRAM 通道……）的利用率放在一张表里看，谁忙谁闲一目了然。对应 case-003 的 step 2：“DMA 41%, NoC 38%, CH0 99%, 其余通道 <2%”。

为什么这两步是“固定”的，两个原因：

1. 反正每个 case 都要看。 差距多大、瓶颈在哪个资源，是任何诊断都绕不开的起点。既然必看，就不值得每次让 LLM 花一次提议，直接写死。
2. 这两步不产生额外成本。 它们都是 L0 视图，用同一次仿真的 trace/counter 就能算出来，不用重新仿真。

它跟检索的关系就接上了：这两步的产出恰好就是 signature 的关键字段——瓶颈资源（“DRAM通道”），以及提取器从利用率矩阵直接算出的 dmc.rd_bw.max: 99、dmc.rd_bw.min: 0.5、dmc.rd_bw.var: 1800。（signature 里的“瓶颈资源自身效率”这一位要到第 3 步查完槽位账本才有——检索用的始终是当前已凑出的特征，凑到哪步查到哪步。）所以起手步骤跑完，新 case 才有足够的特征去做真正的历史链检索——这就是上面流程图把“真正的检索”放在起手之后的原因。
